# 后续工作

每轮修改应包含明确的设计理由、代码变更和能覆盖失败路径的测试。

## 1. 真实模型与项目材料

- 准备可合法处理的项目材料：日志、变更、复现步骤和人工确认原因；保留部分信息不足案例。
- 配置 Live 模式，验证至少两类工具的真实调用。
- 在可控环境复现故障，保留输入、证据和失败轨迹。
- 对比直接调用模型与工具流程，记录模型、提示词、数据集、耗时和 usage。
- 增加引用缺失、空工具结果、优先级错误、超时等测试。

验收：至少一个真实故障有可复查的人工定位结果；工具失败不伪造成功；信息不足时不把假设写成已确认根因。

## 2. 只读连接器与外部工单

- 先支持一个 GitHub 或 GitLab 连接器，只允许用户指定的仓库、commit/PR 和路径。
- 将日志与实际 PR 关联，再考虑告警来源。
- 先生成可复制的工单内容，之后才接审批后的真实 Issue 创建。
- 设计远程写入状态、请求指纹、回执和异常恢复；不能仅靠重试避免重复写入。

## 3. 检索与评测

- 导入 README、接口契约、手册和已解决工单，保留来源与权限。
- 支持文档切分、版本、增量更新和删除。
- 先测关键词基线，再评估 embedding、pgvector、混合检索和 reranker 的收益。
- 分离调试集与保留集，标准答案不能进入模型可检索内容。
- 使用同一模型和数据比较直接问答、固定流程和动态工具选择。

关注任务完成率、原因判断、检索召回、引用支持度、合理拒答、工具失败率、延迟和成本。

## 4. 运行与试用

- 实际验证 PostgreSQL，补 Alembic 迁移和备份演练。
- 将任务移入 worker；出现并发需求时再引入队列、租约、超时、重试和死信。
- 增加身份、角色和来源授权；共享令牌不适用于多用户。
- 接入调用 trace，记录模型和工具 attempt 与预算。
- 让实际使用者完成任务，收集证据可读性和工单修改流程的问题。

## 5. 演示材料

- 架构图和关键取舍。
- 包含失败或信息不足场景的现场演示。
- 固定测试集和可复现实验结果。
- 优化前后的对比。
- 一份问题复盘：假设、证据、修改、验证。

不要虚构线上指标、用户数量或接入范围。多 Agent、微调、Kubernetes 和模型训练仅在需求明确时再补。
